> 定稿：2026-09-28 与用户对齐（含二次修订：管理台并发配置 + 研究流水线升级为 Perplexica 完整复刻版）
> 三次修订：2026-09-29 全链路移除 maxTokens（仅 Anthropic 留协议必填的 8192 占位）+ `LLM_TIMEOUT` 60s 放宽为 600s 且明确不做自动重试
> 前置文档：同日本仓库完成的「反馈+教学」批次（搜索降级重试链 + 诊断回传 + linkseek-usage 技能），改动尚未提交，见阶段 0。

## 0. 背景与目标

`web_search_answer` 等四个慢工具（平均耗时 11~40s）在同步调用时阻塞调用方整轮对话；深度研究类搜索（多轮迭代，1~3 分钟）在同步模式下完全不成立。本期引入**异步任务体系**：

- 四个慢工具加 `defer` 参数（默认 `false` 行为不变），传 `true` 立即返回任务 ID
- 新增纯异步的 `web_research` 深度研究工具：服务器上跑 Perplexica 式完整流水线（多轮迭代 + LLM 结果筛选 + 长文分块蒸馏 + 充分性判断）——**异步化是放开完整复刻的前提**：任务已脱手，服务器跑几轮都不阻塞调用方
- 共用一个 `get_result` 取结果工具（带进度；不实现服务端长等待——智能体自己 sleep 或先干别的）
- LLM 成本记账归集到提交任务的 Key，Dashboard 增加 Key 维度 AI 成本视图 + **并发上限设置页**（部署者按服务器性能自调）

设计对齐（对话定稿，不再开放）：
- **不分裂工具**：用 `defer` 布尔参数而非「同步版/异步版」两套工具，工具总数只净增 2（`web_research`、`get_result`）
- **不做长轮询**：`get_result` 立即返回状态；等待策略由调用方（智能体）自理，skill 中教学「未完成 → sleep 15-30s 或先干别的活」
- **结果格式兼容**：任务完成后 `get_result` 返回的内容与对应同步工具原本的返回格式完全一致

## 1. 已拍死的决策（无开放选择题）

| 决策点 | 结论 |
|---|---|
| defer 参数 | `defer?: boolean`，默认 `false`（不传 = 现有行为，完全向后兼容） |
| 覆盖工具 | `web_search_and_fetch`、`web_search_answer`、`web_fetch_answer`、`web_fetch_render` 四个；`web_search`/`web_fetch`（秒级）不做 |
| 任务 ID | `task_` + 12 位随机串（nanoid 或等价实现，实现时自选） |
| 存储 | v1 纯内存 Map，不进数据库；重启丢任务，`get_result` 返回明确话术 |
| TTL | 任务完成态保留 60 分钟，过期返回「已过期」；访问时惰性清理 + 每分钟定时清扫（实现方式自选） |
| **并发上限（管理台可配）** | 新增 `SystemSetting` 表（key-value）存运行时配置；本期存两个键：`taskConcurrencyPerKey`（默认 3）、`taskConcurrencyGlobal`（默认 10）；TaskManager 热读取（每次 submit 时查，或 30s 缓存，实现自选）；管理台设置页可改，改完即时生效 |
| **研究流水线（Perplexica 完整复刻版）** | 见 §4 阶段 3 的流水线详设；`depth` 三档：`fast`（1 轮、抓 3 源、无蒸馏）/ `standard`（3 轮、抓 5 源、蒸馏，默认）/ `deep`（5 轮、抓 8 源、蒸馏） |
| 研究工具 LLM | 复用 `resolveProvider` 默认 Provider（可用 `model` 参数换）；预处理温度 0（防发散，Perplexica 同款做法）。**全链路不设 maxTokens 输出上限**（用户明确否决截断设计——上限看似安全实为累赘）；存量 `config.LLM_MAX_TOKENS` 设计本期一并移除（见阶段 3 前置项与替代表） |
| LLM 超时 | `LLM_TIMEOUT` 默认 **60s → 600s（10 分钟）**，全链路统一（research 流水线不单独设超时）；**不做自动重试**（用户否决，失败即失败）。语义说明：本项目 LLM 调用全为非流式，无法区分「在写长文」与「挂死」，故为总时长闸而非空闲超时（ZCode 的 10 分钟空闲超时依赖流式事件重置，我们不适用）；量级取 ZCode 同款 10 分钟，兜底场景是服务端卡死无响应 |
| JSON 解析容错 | 预处理/筛选/充分性判断的 JSON 输出解析失败时降级策略见阶段 3（原则：降级继续，不让整个任务 fail） |
| 成本记账 | 每个任务完成时写**一条聚合 UsageLog**（provider/model/token/cost 汇总该任务全部 LLM 调用），keyId 归提交任务的 Key；工具名记任务类型对应名 |
| 进度展示 | 状态机 `queued → running(带阶段文案) → done / failed`；research 的进度含轮次与来源数（见 §4） |
| Dashboard | 两个新增：①「Key AI 成本」视图（表格：Key 名、AI 请求数、输入/输出 token、成本合计）②「任务设置」页（并发配置：每 Key 并发、全局并发，含保存与即时生效）；均不做复杂图表 |
| 新工具命名 | `web_research`（纯异步）与 `get_result`（全类型共用） |

## 2. 明确不做清单（本期诱惑项）

- ❌ `wait_seconds` 长轮询参数（等无 shell 的客户端接入再加，向后兼容）
- ❌ 任务持久化到数据库 / 重启恢复
- ❌ 公开 REST API（/v1）的异步端点
- ❌ `web_search`、`web_fetch`、`list_models` 的 defer 化
- ❌ **本地 embedding 模型（transformers.js）**：相关性过滤/去统一律用 LLM 判断替代——避免引入模型下载与常驻内存依赖；未来若要零 LLM 成本过滤再评估
- ❌ Perplexica 的天气/股票/计算 widget 与「跳过搜索」分类（调用方是 Agent，早已决策要搜）
- ❌ SearXNG 引擎治理（升级镜像/裁引擎，独立批次）
- ❌ `public/docs.html` 门户页新增工具说明（随部署批次一起做）
- ❌ 不 push、不发 PR（仅本地提交，推送由用户决定）

### 阶段 3：`web_research` 研究流水线 `src/research/pipeline.ts`（新建）

**前置项：LLM 调用参数清理——移除存量 maxTokens 约束 + 超时放宽**（2026-09-28 全量 grep 核实 maxTokens 引用面；09-29 追加超时决策）。约束的根在适配器层——四个适配器解构时自带 `maxTokens = 2000` 默认值，只删调用点删不掉约束：
1. `src/llm/types.ts` — `ChatOpts` 删除 `maxTokens` 字段（接口不再暴露此参数）
2. 四个适配器删去 `maxTokens` 解构默认值与 API 字段：`openai.ts`（`max_tokens`）、`openai-responses.ts`（`max_output_tokens`）、`gemini.ts`（`maxOutputTokens`）——这三家协议字段可省略，省略即不限；`anthropic.ts` 特殊：协议要求 `max_tokens` 必填，固定传 `8192`（在售 Claude 模型输出上限均 ≥8192，此为协议占位而非截断设计，若长回答被截再上调）
3. `src/config.ts` 删除 `LLM_MAX_TOKENS` schema 项
4. `src/tools/web-search-answer.ts:235`、`src/tools/web-fetch-answer.ts:123` 删去 `maxTokens: config.LLM_MAX_TOKENS` 传参
5. `.env.example` / `.env.production.example` 已核查无此变量行，无需改动
6. `src/config.ts` `LLM_TIMEOUT` 默认 `60_000` → `600_000`（10 分钟）；四个适配器解构兜底默认 `30_000` 一并对齐 `600_000`（防未来调用点漏传时被 30s 误杀）；**不加重试逻辑**（现状本就零重试，保持）

**输入**：`question`（自然语言或关键词均可）、`depth`（`fast|standard|deep`，默认 `standard`）、`model`（LLM Provider，同现有工具语义）。

**流水线**（Perplexica 式，按 depth 控制深度）：

1. **预处理**（1 次 LLM，温度 0）：输出 JSON `{ standaloneQuestion, queries[1~3], language?, categories?, timeRange? }`。`standaloneQuestion` 吸收 Perplexica 的独立问题改写（把依赖上下文的问句补全为自包含）；查询要求关键词式（prompt 明确「不是句子」）。**JSON 解析失败 → 降级**：直接用原始 question 当唯一查询，继续流程
2. **循环**（`maxRounds` 由 depth 决定：1/3/5）：
   a. 并行搜索本轮查询（复用 searchWithFallback）
   b. **LLM 结果筛选**（1 次调用/轮）：对候选结果（标题+摘要+URL）按相关性/来源权威/多样性打分，输出选中下标列表（目标抓取数 = depth 决定的 3/5/8，累计去重后）。**解析失败 → 降级**：按 score 排序取前 N
   c. 抓取选中页面（并行，复用 WAF 自动降级渲染逻辑）
   d. **分块蒸馏**（standard/deep 才有；每源 1~n 次调用）：正文按 ~4000 字符切块，逐块让 LLM 按问题意图抽取要点（电报式、保留原始数字与事实，prompt 参考 Perplexica information extractor 措辞）；fast 档直接截 4000 字符（现状行为）
   e. **充分性判断**（1 次调用/轮）：LLM 判断现有要点能否回答问题；输出 `{ sufficient: bool, followUpQueries[] }`。充分 → 跳出循环；不足且还有轮次 → 用 followUpQueries 进入下一轮（prompt 要求「先宽后窄」）；**解析失败 → 降级**：视为充分，直接进综合
3. **综合回答**（1 次调用）：复用 `web_search_answer` 的 system prompt 与来源编号格式，输出回答 + 来源列表（与 web_search_answer 同构）

全轮皆空 → 返回空结果报告（复用 buildEmptyReport，diagnostics 汇总各轮尝试）。

**门禁**：typecheck + build；本地栈可用时用 2~3 个真实问题按三档 depth 各跑一遍，人工看回答/来源/轮次是否符合档位设定。
